# LangChain + RAG 기반 소비 피드백 서비스에서 RAG 문서를 활용하는 방법

가장 추천하는 방식은 **5번 RAG 검색 결과를 7번 프롬프트에 “원문 문서”로 넣지 말고, 5번과 7번 사이에 `5.5 근거 카드화` 단계를 추가하는 것**입니다.

즉, 현재 구조를 이렇게 바꾸는 게 좋습니다.

```text
4. 지표 해석
   └─ 패턴탐지 / 문제 식별 / 원인 해석 / 개선 포인트

5. RAG 검색
   └─ 문제별로 유사 문서 검색

5.5. 검색 문서 → 피드백용 근거 카드로 변환
   └─ 통계 인사이트 / 유사 사례 / 절약 행동 / 복지 혜택 / 주의사항 추출

6. 유저 메모리 주입

7. 피드백 생성
   └─ 유저 지표 + 지표 해석 + 근거 카드 + 메모리를 조합해 문구 생성
```

LangChain 문서에서도 RAG는 검색된 외부 지식을 생성 단계의 컨텍스트로 공급하는 구조로 설명되고, retriever는 쿼리를 받아 `Document` 목록을 반환하는 인터페이스로 설명됩니다. 다만 소비 피드백 서비스에서는 검색 문서를 그대로 넣는 것보다, 문서에서 “사용자 피드백에 쓸 수 있는 주장·행동·주의사항”만 추출해서 넣는 편이 훨씬 안정적입니다.

참고: [LangChain Retrieval 문서](https://docs.langchain.com/oss/python/langchain/retrieval)

---

## 1. RAG 문서의 역할을 명확히 나누세요

이 서비스에서 **판단의 1순위 근거는 유저의 실제 결제 지표**여야 합니다.

RAG 문서는 다음 역할로 쓰는 게 좋습니다.

```text
유저 결제 지표:
- 이번 기간에 실제로 무슨 일이 있었는지 판단
- 어떤 카테고리가 문제인지 판단
- 변화율, 빈도, 금액, 반복 패턴 판단

RAG 문서:
- 이 패턴이 어떤 소비 성향과 연결되는지 설명
- 비슷한 사람들의 소비 사례 제공
- 실천 가능한 절약 행동 추천
- 관련 복지/혜택/소비자 주의사항 제안
- 피드백 문구의 설득력과 구체성 강화
```

즉, RAG 문서가 “이 사람은 낭비벽이 있다”를 판단하게 하면 안 됩니다.  
그 판단은 3번, 4번에서 나온 지표 해석이 해야 합니다.

RAG는 이렇게 써야 합니다.

```text
“이번 주 배달 지출이 최근 4주 평균보다 42% 높다”
→ 유저 데이터 기반 판단

“유사 소비 인사이트에서 야근/피로 후 배달 반복은 식비 예산 초과의 흔한 원인으로 분류된다”
→ RAG 기반 보강

“그래서 다음 주에는 화·목 저녁만 배달 허용, 나머지는 냉동식품/밀키트 대체 규칙을 세우자”
→ 행동 제안
```

## 2. 5번 검색 결과를 바로 7번에 넣지 마세요

많은 RAG 서비스가 실패하는 지점이 여기입니다.

```text
검색된 문서 5개를 그대로 프롬프트에 넣음
→ LLM이 중요하지 않은 문장까지 섞어서 사용
→ 문구가 일반론이 됨
→ 유저 지표보다 문서 내용이 더 강하게 반영됨
→ “나한테 하는 말” 느낌이 약해짐
```

대신 검색 결과를 아래처럼 **근거 카드**로 바꾸세요.

```json
{
  "issue_id": "weekly_food_delivery_spike",
  "source_type": "saving_tip",
  "source_title": "배달비 절약 행동 가이드",
  "usable_claim": "배달 지출은 피곤한 저녁 시간대에 반복될 때 통제하기 어렵다.",
  "user_connection": "이번 주 유저의 배달 결제는 전주 대비 38% 증가했고, 평일 저녁 결제가 많다.",
  "recommended_action": "평일 배달 허용일을 주 2회로 제한하고, 나머지 요일에는 미리 정한 대체 식사를 둔다.",
  "tone_hint": "따끔하지만 비난하지 않기",
  "caution": "건강 상태나 근무 패턴을 단정하지 말 것"
}
```

7번 피드백 생성 프롬프트에는 문서 원문이 아니라 이런 카드를 넣는 게 좋습니다.

## 3. 근거 카드 스키마를 정하세요

추천하는 스키마는 아래와 같습니다.

```python
from typing import Literal, Optional
from pydantic import BaseModel, Field

class EvidenceCard(BaseModel):
    issue_id: str = Field(description="이 근거가 연결되는 소비 문제 ID")
    source_type: Literal[
        "saving_tip",
        "welfare_benefit",
        "large_card_insight",
        "consumer_agency_report",
        "internal_user_insight"
    ]
    source_title: str
    source_id: str

    relevance_reason: str = Field(description="왜 이 문서가 현재 유저 문제와 관련 있는지")
    usable_claim: str = Field(description="피드백에 쓸 수 있는 핵심 주장")
    user_connection: str = Field(description="유저 지표와 연결되는 부분")
    recommended_action: str = Field(description="유저에게 제안할 구체 행동")
    caution: Optional[str] = Field(description="단정하거나 과장하면 안 되는 부분")
    tone_hint: Optional[str] = Field(description="문구 톤 가이드")
    confidence: Literal["high", "medium", "low"]
```

LangChain은 구조화된 출력을 JSON, Pydantic 모델, dataclass 등 애플리케이션에서 바로 사용할 수 있는 형태로 받을 수 있다고 설명합니다. 이런 중간 결과를 구조화하면 7번 생성 프롬프트가 훨씬 안정적입니다.

참고: [LangChain Structured Output 문서](https://docs.langchain.com/oss/python/langchain/structured-output)

## 4. 문서 유형별 사용법을 다르게 가져가세요

현재 RAG화한 문서들이 서로 성격이 다릅니다. 그래서 같은 방식으로 쓰면 안 됩니다.

| 문서 유형 | 피드백에서의 역할 | 주의점 |
|---|---|---|
| 절약 팁 | 바로 실행 가능한 행동 제안 | 너무 뻔한 팁은 제거 |
| 복지 혜택 | 조건에 맞을 가능성이 있는 혜택 안내 | “받을 수 있다”가 아니라 “확인해보자”로 표현 |
| 300만명 카드 데이터 인사이트 | 유저 패턴을 더 넓은 소비 패턴과 비교 | 유저를 평균에 억지로 맞추지 않기 |
| 한국소비자원 소비 보고서 | 소비자 피해, 충동구매, 구독, 할부, 가격 비교 주의사항 | 훈계보다 예방 안내로 사용 |
| 앱 유저 100명 트랜잭션 인사이트 | 유사 사용자 사례, 앱 내부 패턴 | 표본이 작으므로 강한 일반화 금지 |

예를 들어 복지 혜택 문서가 검색되면 이렇게 쓰는 게 좋습니다.

### 나쁜 예

```text
민수님은 청년 교통비 지원을 받을 수 있어요.
```

### 좋은 예

```text
민수님처럼 교통비 비중이 꾸준히 높은 경우에는 청년 교통비 지원이나 지역 교통비 혜택을 확인해볼 만해요. 단, 거주지와 소득 조건에 따라 달라질 수 있으니 이번 주에 한 번만 확인해봐요.
```

## 5. 7번 프롬프트에는 “문서 사용 규칙”을 강하게 넣으세요

7번 프롬프트에 RAG 내용을 넣을 때는 아래 규칙을 넣는 걸 추천합니다.

```text
[외부 근거 사용 규칙]

1. 유저의 실제 결제 지표와 지표 해석을 최우선 근거로 사용한다.
2. RAG 근거 카드는 설명, 사례, 행동 제안을 보강하는 용도로만 사용한다.
3. 근거 카드의 내용이 유저 지표와 직접 연결되지 않으면 사용하지 않는다.
4. 복지 혜택은 확정적으로 말하지 말고 “확인해볼 만하다”로 표현한다.
5. 내부 유저 100명 데이터는 “일부 유사 사례” 수준으로만 표현한다.
6. 검색 문서의 내용을 그대로 나열하지 말고, 유저의 상황에 맞게 재작성한다.
7. 각 피드백 문단은 반드시 다음 구조를 따른다.

   지표 언급 → 소비 패턴 해석 → RAG 근거 연결 → 개선 행동 제안
```

이 구조가 중요합니다.

```text
지표 언급:
이번 주 카페 지출이 최근 4주 평균보다 31% 높아요.

소비 패턴 해석:
큰돈을 한 번에 쓴 건 아니지만, 소액 결제가 반복되면서 누적된 패턴이에요.

RAG 근거 연결:
유사 소비 인사이트에서도 카페·편의점 같은 소액 반복 지출은 체감보다 실제 지출이 커지는 항목으로 자주 나타나요.

개선 행동:
다음 주에는 출근길 커피를 주 2회만 허용하고, 나머지 날은 회사 커피나 텀블러로 대체해봐요.
```

## 6. 최종 피드백 생성 프롬프트 예시

아래처럼 구성하면 좋습니다.

```text
너는 카드 결제 데이터를 바탕으로 사용자의 소비 습관을 분석하고,
따끔하지만 애정 있는 소비 피드백을 작성하는 코치다.

너의 목표:
- 사용자가 자신의 소비 문제를 쉽게 이해하게 한다.
- 비난하지 않는다.
- 구체적인 행동 변화를 유도한다.
- 일반적인 절약 조언이 아니라, 실제 결제 지표에 기반한 피드백을 작성한다.

[사용자 정보]
이름: {name}
직업: {job}
연봉: {salary}
페르소나: {persona}
절약 목표: {saving_goal}

[보고서 유형]
{report_type}  # daily / weekly / monthly

[결제 지표]
{payment_metrics}

[지표 해석 결과]
{metric_interpretation}

[이전 메모리]
{user_memory}

[RAG 근거 카드]
{evidence_cards}

[작성 규칙]
1. 결제 지표와 지표 해석을 가장 중요한 근거로 사용한다.
2. RAG 근거 카드는 피드백을 구체화하기 위한 보조 근거로만 사용한다.
3. RAG 근거 카드가 유저 지표와 직접 연결되지 않으면 사용하지 않는다.
4. 사용자의 이름을 자연스럽게 1회 사용한다.
5. 잔소리는 따끔하게 하되, 인격 비난은 하지 않는다.
6. 개선 행동은 오늘/이번 주/이번 달에 바로 할 수 있는 행동으로 제시한다.
7. 복지 혜택은 확정 표현을 쓰지 않는다.
8. 출력은 아래 형식을 따른다.

[출력 형식]
{
  "title": "...",
  "summary": "...",
  "nagging": "...",
  "pattern_analysis": "...",
  "recommended_actions": ["...", "..."],
  "goal_connection": "...",
  "next_check_point": "..."
}
```

## 7. 실제 문구 반영 예시

### 입력 상황

```text
보고서 유형: 주간
문제:
- 배달/외식 지출 전주 대비 +48%
- 최근 4주 평균 대비 +36%
- 평일 저녁 8시 이후 결제가 많음
- 절약 목표: 3개월 안에 비상금 100만원 만들기

검색된 근거 카드:
- source_type: large_card_insight
- usable_claim: 평일 저녁 배달 지출은 피로 기반 소비로 반복될 가능성이 높다.
- recommended_action: 배달 허용 요일을 정하고, 대체 식사를 미리 준비한다.
```

### 좋지 않은 출력

```text
배달을 줄이세요. 배달은 돈이 많이 듭니다. 절약을 위해 집밥을 먹는 것이 좋습니다.
```

이건 RAG를 써도 너무 일반적입니다.

### 좋은 출력

```text
이번 주는 배달앱이 지갑을 꽤 세게 흔들었어요. 배달/외식 지출이 전주보다 48%, 최근 4주 평균보다도 36% 높았고, 특히 평일 저녁 8시 이후 결제가 반복됐습니다.

이건 단순히 “맛있는 걸 먹었다”기보다, 피곤한 시간대에 결정을 미루다가 배달로 해결한 패턴에 가까워요. 유사 소비 인사이트에서도 이런 평일 저녁 배달 반복은 식비 예산을 무너뜨리는 대표적인 흐름으로 잡힙니다.

다음 주에는 배달을 아예 끊기보다 화·목 2번만 허용해보세요. 나머지 평일 저녁은 냉동식품, 밀키트, 편의점 도시락처럼 “주문 버튼 누르기 전 대안”을 미리 정해두는 게 현실적입니다. 비상금 100만원 목표를 생각하면, 이번 주 배달 증가분만 잡아도 목표에 꽤 가까워질 수 있어요.
```

여기서 RAG는 “평일 저녁 배달 반복은 식비 예산 초과로 이어지기 쉽다”는 해석과 “배달 허용 요일을 정한다”는 행동 제안에 반영되었습니다. 하지만 핵심은 여전히 유저의 실제 지표입니다.

## 8. 일일/주간/월간마다 RAG 활용 방식을 다르게 하세요

### 일일 보고서

일일은 너무 많은 RAG 근거를 쓰면 부담스럽습니다.

```text
목표:
- 어제 소비를 바로 돌아보게 하기
- 오늘 바꿀 행동 1개 제안
```

RAG 활용:

```text
절약 팁 1개
소비 패턴 설명 1개
```

예시:

```text
어제 편의점 결제가 4번 있었어요. 금액은 크지 않아 보여도, 이런 소액 반복 지출은 체감보다 누적이 빠른 편입니다. 오늘은 편의점에 들어가기 전에 “진짜 필요한 물건 1개만 사기” 룰을 걸어보세요.
```

### 주간 보고서

주간은 패턴 분석에 가장 적합합니다.

```text
목표:
- 반복 카테고리 발견
- 원인 추정
- 다음 주 행동 규칙 제안
```

RAG 활용:

```text
유사 소비 인사이트
절약 행동
소비자원 리포트
```

예시:

```text
이번 주 카페 지출은 단순한 취향 소비라기보다 출근 루틴에 붙은 자동 지출에 가까워 보여요. 유사 소비 패턴에서도 카페·편의점처럼 작은 결제가 반복되는 항목은 월말에 체감보다 큰 금액으로 남는 경우가 많습니다.
```

### 월간 보고서

월간은 구조적인 개선에 적합합니다.

```text
목표:
- 예산 재설계
- 절약 목표와 연결
- 복지/혜택/구독/고정비 점검
```

RAG 활용:

```text
복지 혜택
장기 소비 인사이트
고정비 절감 팁
소비자 피해/구독 주의사항
```

예시:

```text
이번 달 교통비와 통신비처럼 줄이기 어려운 고정성 지출의 비중이 높았어요. 무작정 아끼기보다, 청년 교통비 지원이나 통신비 할인 조건처럼 받을 수 있는 혜택이 있는지 확인해보는 쪽이 더 현실적입니다.
```

## 9. 검색 쿼리도 “문제별”로 만들어야 합니다

5번에서 RAG 검색할 때 단순히 이렇게 검색하면 품질이 떨어집니다.

```text
"이번 주 소비가 많음 절약 팁"
```

이렇게 검색해야 합니다.

```text
"30대 직장인 평일 저녁 배달 지출 증가 식비 절약 행동"
"카페 편의점 소액 반복 결제 소비 패턴 절약 팁"
"월간 교통비 비중 높음 청년 교통비 혜택 확인"
"구독 서비스 자동결제 증가 소비자 주의사항"
```

더 좋은 방식은 4번 결과에서 `issue_card`를 만들고, issue별로 쿼리를 생성하는 것입니다.

```json
{
  "issue_id": "cafe_small_repeat",
  "category": "카페",
  "pattern": "소액 반복 결제",
  "metric": "최근 4주 같은 요일 평균 대비 +29%",
  "persona": "직장인",
  "goal": "월 30만원 저축",
  "query_intent": [
    "유사 소비 패턴",
    "소액 반복 지출 절약 행동",
    "직장인 카페 지출 줄이는 방법"
  ]
}
```

그리고 각 issue마다 검색합니다.

```text
issue 1: 카페 소액 반복
issue 2: 배달 지출 급증
issue 3: 택시비 증가
issue 4: 구독 자동결제 증가
```

이렇게 해야 최종 피드백이 “전체적으로 아끼세요”가 아니라 “이번 주 문제는 카페와 배달이고, 각각 이렇게 바꾸세요”가 됩니다.

## 10. 검색 후 rerank / compression을 붙이는 것도 추천합니다

검색된 문서가 많거나 청크가 길면, 7번 프롬프트에 들어가기 전에 관련 없는 부분을 줄여야 합니다. LangChain 문서에서도 reranker를 `ContextualCompressionRetriever`와 함께 사용해 검색 결과를 재정렬하거나 압축하는 예시를 제공합니다.

참고: [LangChain Cohere Reranker 문서](https://docs.langchain.com/oss/python/integrations/retrievers/cohere-reranker)

추천 흐름은 이렇습니다.

```text
1차 검색: 넓게 검색, k=10~20
↓
rerank: 현재 issue와 가장 관련 있는 문서 상위 3~5개 선정
↓
compression/extraction: 문서에서 필요한 문장·행동·주의사항만 추출
↓
evidence_card 생성
↓
피드백 생성 프롬프트에 주입
```

## 11. 최종적으로는 이 구조가 제일 좋습니다

```text
[결제 데이터]
   ↓
[지표 생성]
   ↓
[지표 해석 LLM]
   ↓
issue_cards 생성
   - 문제 카테고리
   - 변화율
   - 반복 패턴
   - 원인 추정
   - 개선 방향

   ↓

[issue별 RAG 검색]
   ↓
[rerank / compression]
   ↓
[evidence_cards 생성]
   - 관련 주장
   - 유저 지표와 연결점
   - 행동 제안
   - 주의사항
   - 출처 유형

   ↓

[최종 피드백 생성]
   입력:
   - 유저 정보
   - 결제 지표
   - issue_cards
   - evidence_cards
   - 유저 메모리

   출력:
   - 잔소리
   - 패턴 분석
   - 개선 행동
   - 목표 연결
   - 다음 체크포인트
```

핵심은 이것입니다.

```text
RAG 문서는 “답변의 주인공”이 아니라
유저 지표를 더 설득력 있게 말하게 해주는 “보조 코치”여야 합니다.
```

그래서 7번에서 검색 문서를 직접 넣는 대신, **검색 문서 → 근거 카드 → 피드백 문구**로 한 번 가공해서 쓰는 구조를 추천합니다.
